# zcbot-multiprocessing（zcbot-mp）架构草案

## 硬约束

- 全新仓库。原 `zcbot` 保持单进程，一行不改。
- zcbot 现有的 `dual_process` 只是技术参考：借它的 IPC 边界设计，不继承它的代码、配置和兼容负担。

## 1. 定位

**一句话**：把「一个插件能把整个进程拖垮」变成「一个 worker 崩了只影响它承载的插件，Core 自动隔离或重启，协议与 Web 不中断」。

适用边界：

1. 插件来源杂、数量多、升级频繁，单进程故障半径不可接受；
2. 需要长时间不中断运行（协议接入 / Web 常驻）；
3. 目标是**单机多进程**——跨机编排属于另一层，不在这个仓库里做。

## 2. 进程模型

| 角色 | 持有 | 不持有 |
|------|------|--------|
| Core | 真实 DB、协议接入、Web、全局路由表、Worker 监督器 | 用户插件执行 |
| Worker | 插件实例、本地 hook / 命令注册表、事件队列 | 真实 DB、协议连接、Web |
| Gateway（可选，v2+） | 多机转发 | 任何业务状态 |

**隔离粒度**建议做成可配置，默认「分组」：

- 一插件一进程：隔离最好，但插件多时进程数和内存开销大、启动慢；
- 分组共享 worker：折中，组内仍会互相影响；
- 默认策略：按插件声明的 `isolation_group` 分组，未声明的进同一默认组；关键/不稳定插件显式独占。

Core 维护 `plugin -> worker_id` 映射；事件按订阅扇出，命令按 `command -> plugin -> worker` 路由。

## 3. IPC 设计

从 zcbot 借鉴的部分：JSON-RPC 信封、`multiprocessing.connection` 回环 + authkey、同步 `call` / 异步 `acall` 双接口。

从 1:1 到 1:N 必须新增：

- **身份与注册**：worker 握手带 `worker_id`，上报插件清单 / 命令 / 订阅；Core 聚合全局注册表，worker 崩溃即注销其全部注册项。
- **请求超时与取消**：每个请求带 deadline，Core 统一超时；插件卸载时取消在途请求，避免「卸了还在跑」。
- **事件序号与背压**：Core→Worker 事件带 seq；每 worker 一个有界队列，慢 worker 按策略丢弃或降级，不允许拖垮 Core 的事件循环。
- **崩溃拉起与熔断**：滑动窗口内重启次数超限就把该 worker 的插件 quarantine（停止并在 Web 上可见），不再无限重启。
- **日志桥接**：worker 日志带 `worker_id` 汇入 Core，否则多进程日志根本没法查。

## 4. 插件 API 契约

保留 zcbot 的 `ctx.command` / `ctx.hook` / `ctx.db` 写法风格，但新仓库自己定义契约，不做二进制兼容。

三条硬决定（都来自 zcbot 踩过的坑）：

1. **DB 以 async 为主**：`await ctx.db.query(...)`；同步方法只做兼容层。否则一个慢 RPC 就卡死整个 worker 事件循环。
2. **短路线索是硬契约**：`trigger_sync` 与 `trigger_async` 必须同语义；Guard 抛异常按 fail-closed 处理而不是放行。zcbot 里这两条都是后补的，新仓库从第一天就钉死。
3. **不暴露全局框架引用**：插件拿不到 `ctx._framework` 这种对象，宿主级接口（停机、卸载别人）走显式的、带权限的 API。

## 5. 数据访问

- 所有 DB 访问经 Core 代理；**事务必须显式**（`with ctx.transaction():`），Core 保证同一事务内串行，避免多 worker 交叉写。
- SQLite 单写者：写全部回 Core 串行；读第一版不做只读副本，保持简单。
- 批量写沿用「Core 侧攒批 + 坏行隔离」，不让一条坏数据毁掉整批。

## 6. 起步路径

| 阶段 | 内容 | 验收标准 |
|------|------|----------|
| 一 · 骨架 | Core + 单 Worker，IPC 跑通，插件 API 最小集 | 能收发一条消息；kill worker 后 Core 自动拉起且 Web 不掉 |
| 二 · 隔离 | N worker、路由、命令聚合、quarantine | kill 一个 worker，其它插件继续工作，被杀插件的注册项消失 |
| 三 · 生产化 | 背压、可观测、单 worker 热替换 | 压测下慢 worker 不拖垮 Core；可不停机替换单个 worker |

## 7. 明确不做

1. 不做跨机分布式 / 集群调度；
2. 不做安全沙箱——进程隔离不等于安全边界，恶意插件仍可通过 RPC 调 Core；
3. 不做与 zcbot 插件的格式兼容，只保留写法风格；
4. 不做共享内存 / 零拷贝 RPC，先正确再谈性能。
