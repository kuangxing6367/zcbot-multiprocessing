# zcbot-multiprocessing（zcbot-mp）架构草案

> 本文只做设计，不写实现代码，不改动任何现有文件。
> 前置约束（贯穿全文，不再重复）：
> - `zcbot-mp` 是**全新仓库**，独立仓库、独立发布、独立版本号；不是 zcbot 的分支、wrapper 或配置项。
> - 原仓库 `zcbot` **保持单进程现状，一行不改**；其 `dual_process` 仅作为「已验证过的 IPC 边界」技术参考。
> - `excerpt_dual.md` 是唯一事实来源，下面凡标注「借鉴」的都来自它，凡标注「不借鉴/改造」的都是本仓库的新决策。

---

## 0. 先说清楚：从 dual_process 借鉴什么、不借鉴什么

| 维度 | dual_process 的做法（参考） | zcbot-mp 的决策 | 原因 |
|------|---------------------------|-----------------|------|
| 进程边界 | Core 持有真实资源，Host 跑插件，IPC 远程代理 | **借鉴并推广**：Core + N Worker，边界语义一致 | 已被验证的切分点，风险最低 |
| 传输 | `multiprocessing.connection` + pickle 帧 + authkey 摘要鉴权，零三方依赖 | **借鉴**：阶段一沿用；但自研 `protocol` 层（版本化信封），不复用其代码 | 零依赖、回环可信，够用；契约要自己掌握 |
| 角色分派 | `role` 三态 + `dual_process.enabled` 门控 + `__plugin_meta__['process']` | **不借鉴**：新仓库没有 `dual_process` 开关，也没有三态 role；改为「清单声明 + 启动拓扑」 | 新仓库默认就是多进程，不需要兼容开关 |
| 重启限流 | `max_restarts=5` / `restart_interval=30` | **借鉴并增强**：限流窗口 + 熔断禁用 | 原做法只限流、不熔断，抖动插件会永远反复重启 |
| 事件攒批 | `event_batch_max=64` / `event_batch_delay_ms=5` | **借鉴但改粒度**：按 worker 独立攒批，不再全局一批 | 避免慢 worker 拖住快 worker 的队头 |
| 远程代理 | `RemoteDatabase / RemoteApiCaller / RemoteRouteRegistry / RemoteTx` | **借鉴形态，重写契约**：本仓库自定义 `mp.Context` API v1 | 新仓库自己定义契约，不承诺与 zcbot API 逐签名兼容 |
| Host 数量 | 1（1:1） | **改造为 1:N** | 这是本仓库存在的根本理由 |

## 1. 定位：到底解决什么 zcbot 解决不了的问题

**一句话定位**：zcbot-mp 把「用户插件」变成可独立失败的单元——用 1:N worker 把插件故障域从「整个进程」缩小到「单个 worker」，使任一插件崩溃、卡死或内存泄漏都不再拖垮协议接入、Web 后台和调度器；它不改造 zcbot，而是另起炉灶。

zcbot 单进程（以及其实验性 `dual_process`）的硬限制是：要么所有插件共用一个失败域（单进程），要么只有**一个**可重启的插件宿主（双进程）。一旦插件数量多、来源杂，一个坏插件要么拖垮全部，要么只能整体重启宿主。这是配置开关和 1:1 边界解决不了的结构性问题。

**三条明确的适用边界：**

1. **适用：多插件、多来源、需要故障域切分。** 当插件由不同人/第三方提供，且要求「A 崩了 B 照常收事件、网关不断线」时，用 zcbot-mp。
2. **不适用：高频低延迟大对象共享。** 若插件之间需要与核心/彼此做每秒数千次、携带大对象的同步调用，跨进程序列化往返的开销不划算——这类场景留在 zcbot 单进程。
3. **不适用：无法可靠 spawn 子进程或只用本机回环的环境。** 受限容器 / 特殊平台无可用本地 IPC、或只有一个完全可信插件时，多进程纯增成本——留在 zcbot 单进程。

> 判断口诀：**要隔离、能接受一次 RPC 往返 → zcbot-mp；要极致内聚低延迟 → zcbot。**

## 2. 进程模型

### 2.1 三类进程与持有物

```
┌────────────────────────── Core（监督者 + 唯一资源所有者） ──────────────────────────┐
│ 真实 SQLite（唯一写者）│ Worker 注册表 │ 事件路由表 │ 命令注册表 │ 监督器(重启/限流/熔断)│
│ IPC Server │ 单写者队列 │（可选）协议接入端点 │ 全局配置快照                          │
└───────────────┬──────────────────────────┬──────────────────────────┬──────────────┘
                │ IPC(HELLO/订阅/命令/DB)   │                          │（可选拆分）
      ┌─────────┴─────────┐       ┌─────────┴─────────┐      ┌─────────┴─────────┐
      │ Worker-1          │       │ Worker-2          │ ...  │ Worker-N          │
      │ [插件A, B]        │       │ [插件C]           │      │ [插件D(untrusted)]│
      │ 插件实例/本地缓存  │       │ 插件实例/本地缓存  │      │ 插件实例/本地缓存  │
      │ 远程代理(DB/API/总线)│    │ 远程代理          │      │ 远程代理          │
      └───────────────────┘       └───────────────────┘      └───────────────────┘
                        （可选）Gateway：只持 socket/连接状态，转发事件给 Core
```

| 进程 | 持有什么 | **不**持有什么 |
|------|----------|----------------|
| **Core**（1 个，必须） | 唯一 SQLite 写连接/单写者队列；Worker 注册表；事件订阅索引；命令注册表；监督器；IPC 服务端；全局配置快照；（小规模时）协议接入端点 | 不加载/执行任何用户插件；不运行任何 hook/命令回调 |
| **Worker**（N 个，可增减） | 分配给它的插件实例、插件内本地状态与缓存、心跳与收件队列、指向 Core 的远程代理 | 不持有真实 DB 句柄、不直接写 DB 文件；不绑定对外端口；不拥有协议连接；不保存全局命令表 |
| **Gateway**（可选，0/1） | 协议 socket 与连接状态（如 onebot/http_inject/http_api/webui 的接入端）、到 Core 的事件上行通道 | 不执行插件逻辑、不持有 DB、不做事件路由决策——只做「哑」转发 |

**决策**：协议接入默认放在 Core（与参考一致，省一个进程）；当连接数/网络 I/O 成为瓶颈时，按需把接入端拆到 Gateway，Gateway 崩了可由 Core 重新拉起，Worker 不受影响。

### 2.2 插件隔离粒度：三种方案与代价

| 方案 | 做法 | 收益 | 代价 |
|------|------|------|------|
| **一插件一进程** | 每个插件独占一个 Worker | 隔离最强：崩一个只死一个插件；资源可单独限额 | 进程数 = 插件数；每个 Python 解释器约 20–50MB 基线内存；注册表条目与 IPC 连接数线性增长；重启抖动更频繁 |
| **分组（按标签/信任域）** | 按清单里的 `isolation_group` 标签把若干插件放进一个 Worker | 进程数可控；同组插件共享进程内通信，延迟低 | 同组里一个坏插件仍会拖垮整组；需要维护分组规则，隔离粒度变粗 |
| **可配置（推荐）** | 默认按 `isolation_group` 分组；标记为 `untrusted` 或声明 `sandbox=process` 的插件强制独占 Worker | 在隔离强度与资源成本之间按插件逐个权衡；一个策略旋钮即可调 | 调度/注册逻辑最复杂：需要合并清单、动态建组、处理组级熔断；阶段一先不做，阶段二落地 |

**推荐**：以「可配置」为终态目标，但阶段一先实现「全插件单 Worker」把 IPC 跑通（见第 6 节）。分组元数据统一来自插件清单（manifest），不来自类似 zcbot 的 `dual_process.core_plugins` 白名单配置。

## 3. IPC 设计：从 1:1 Host 到 1:N Worker 必须解决的新问题

### 3.0 传输与信封（借鉴参考，自研契约）

- 阶段一沿用 `multiprocessing.connection` + authkey 摘要鉴权（零三方依赖、回环可信）；但**自研** `protocol` 层，定义版本化信封，不复用 dual_process 代码。
- 每个消息信封字段（设计形态，非实现代码）：

| 字段 | 含义 |
|------|------|
| `ver` | 协议版本，不兼容直接拒收 |
| `type` | HELLO / HEARTBEAT / EVENT / EVENT_ACK / CMD_REGISTER / CMD_INVOKE / REPLY / RPC / CANCEL / DB_TX / BYE |
| `worker_id` + `incarnation` | 身份与「第几次重生」，防旧连接重放 |
| `request_id` | 请求-应答关联，拒绝「按 FIFO 假定应答」 |
| `deadline` | 调用方给的绝对超时时刻 |
| `payload` | 序列化负载 |

- 威胁模型写进文档：所有 Worker 都是 Core 本机 spawn 的可信代码，pickle/本地回环可接受；**不**把此边界暴露到网络或不信代码（见第 7 节「不做远程 worker」）。

### 3.1 Worker 身份与注册

- Worker 启动即发 `HELLO`：携带 `worker_id`（Core spawn 时预分配的随机 UUID）、`incarnation`（单调递增）、`pid`、`isolation_group`、插件清单哈希、`api_version`、声明的事件订阅/命令/写意图。
- Core 维护注册表状态机：`REGISTERING → READY → DEGRADED → DEAD`，并记录 `incarnation`。
- 注册必须**幂等**：同 `worker_id` 重连同 `incarnation` 视为同一实例续期；`incarnation` 变小或已被标记的旧实例一律拒绝（防崩溃前的迟到消息污染新实例）。
- 只有进入 `READY` 的 Worker 才被加入路由表与命令表；`DEGRADED/DEAD` 不接收新事件。
- `api_version` 不兼容的 Worker 直接拒绝启动并给出明确诊断（对应第 4 节契约）。

### 3.2 事件路由到哪个 worker

- Core 在注册时聚合所有 Worker 的**声明式订阅**，建立 `event_type → {worker_id...}` 索引；未声明订阅的事件不会被投递（强制显式声明，避免 1:N 下的广播风暴）。
- 三种投递模式，按事件类型配置：
  1. **广播**：如「系统关闭」类事件，投给所有订阅 Worker。
  2. **按 key 分片**：对需要顺序的事件（如按 `group_id`/`user_id`），用 `hash(key) % N` 固定到一个 Worker，保证同 key 顺序性与单写者落点稳定。
  3. **定向**：命令应答类，按 `request_id` 回到发起方。
- 可靠性：事件带 `event_id`，`EVENT_ACK` 驱动**至少一次**投递；消费端按 `event_id` 去重。Worker 重生后 Core 重投未 ACK 事件（对应阶段一验收）。
- 攒批改为**每 Worker 独立** `batch_max / batch_delay_ms`（借鉴 `event_batch_max=64`、`event_batch_delay_ms=5` 的默认值），满批或到点即发，慢 worker 不阻塞快 worker。

### 3.3 命令注册表聚合

- 每个 Worker 注册时上报其 `ctx.command` 声明；Core 构建全局 `命令名 → 归属 worker_id` 表。
- **重名处理**：检测到冲突即拒绝第二个注册并报错（推荐 `plugin.command` 命名空间，冲突时可按命名空间自动消歧，但需显式配置，不静默覆盖）。
- Core 是**唯一命令入口**：外部（Web/协议/Gateway）只调 Core，由 Core 转发给归属 Worker；归属 Worker 不在 `READY` 时，命令返回「不可用」并附带预计恢复状态，**绝不静默改投别的 Worker**。
- 热更新采用写时复制：新注册/注销生成新表后原子替换，进行中的调用按旧表完成，避免竞态。

### 3.4 背压与慢 worker

- 每个 Worker 有**有界**收件队列（默认 1024 条）与高水位线（默认 80%）。
- 到高水位时按事件类别执行可配置策略：可丢弃类（如高频心跳/日志类事件）丢弃并计数；关键类保留并进入 DEGRADED（不再投非关键事件，只保留心跳与控制消息）。**绝不**因为一个慢 worker 而阻塞整条总线。
- 通过 `EVENT_ACK` 延迟持续监测慢 worker；对外暴露 `dropped_total`、`slow_worker` 指标。
- CPU 密集插件用独立进程天然获得 OS 调度隔离；可对 Worker 设 `RLIMIT_AS` 内存上限与 `nice` 值，防止单 Worker 内存泄漏拖垮宿主机。

### 3.5 崩溃拉起与隔离/熔断

- Core 心跳监测（默认 3 次未响应 / 5 秒）判定失联；对假死 Worker 先 SIGTERM 再 SIGKILL，然后重启。
- **重启限流**借鉴参考：`max_restarts=5` / `restart_interval=30`（窗口内最多 5 次）。
- **熔断（新增，区别于参考）**：某 Worker/插件在窗口内重启超过阈值 → 置为 `DISABLED`，从订阅索引与命令表中摘除，发管理事件告警，**不再自动重启**；需管理员显式重新启用。
- 隔离边界：一个 Worker 崩只影响它承载的插件；Core 在 Worker 死亡时清理其租约（DB 事务租约见第 5 节）与未 ACK 事件，并重投给重生实例。

### 3.6 请求超时与取消

- 每个请求带 `request_id`、`deadline`（绝对时刻）与幂等键；Core 设默认超时（如 RPC 3s、命令 30s），调用方可覆盖。
- 应答严格按 `request_id` 关联；超时后的迟到应答直接丢弃并记指标。
- `CANCEL(request_id)`：调用方主动取消 → Core 转发到归属 Worker；Worker 用协作式取消令牌在关键 await 点检查；无法真正中断的调用至少停止向上游回传结果。
- 超时/取消后不得留下「孤儿回调」；命令层保证同一 `request_id` 只产生一次对外结果。

## 4. 插件 API：沿用思路，新仓库自定义契约

沿用 zcbot `ctx.hook / ctx.command / ctx.db` 的**风格**，但由 zcbot-mp 自己定义 `mp.Context` **API v1 契约**。插件通过 manifest 声明能力，Core 据此建表与做路由决策。

### 4.1 manifest 必须声明（注册依据）

| 声明项 | 用途 |
|--------|------|
| `api_version` | 不兼容拒绝加载 |
| `hooks[]`（订阅的事件类型） | 建事件路由索引 |
| `commands[]`（命令名 + 超时建议） | 建全局命令表、检测重名 |
| `write_intents[]`（涉及的写资源） | Core 决定哪些写必须串行化（第 5 节） |
| `isolation_group` / `untrusted` 标记 | 决定隔离粒度（第 2 节） |
| 所需服务（db/api/bus） | 能力校验，缺失即拒绝 |

### 4.2 必须保持「同步语义」的 API

这些是**进程内、加载期、纯本地**的操作，必须同步且确定性，才能在 `HELLO` 前构造出 manifest：

- 注册/声明类：`ctx.hook(event, handler)`、`ctx.command(name, fn)`、`ctx.on_startup / on_shutdown`。
- 本地状态与配置：`ctx.config`（启动期快照，只读）、`ctx.logger`、`ctx.state`（插件进程内私有状态）。
- 说明：`ctx.db` 的**同步外观**（见下）保留，但明确文档化它会阻塞等待 Core 应答。

### 4.3 可以且应当改为「显式异步」的 API

所有**跨进程**操作天然是 RPC，改成显式异步，带 timeout 参数：

- `await ctx.db.query_async(...) / exec_async(...)`（DB 代理）
- `await ctx.api.call_async(...)`（发消息 / RemoteApiCaller）
- `await ctx.bus.emit_async(...)`（跨 worker 事件）
- `await ctx.rpc.call_async(worker_id, ...)`（worker 间定向调用）
- 长耗时命令的处理器本身写成 async，并接受取消令牌。

**兼容策略**：`ctx.db` / `ctx.api` 提供同步外观（内部用 deadline 阻塞等待应答）降低迁移成本，但**强制**要求高频/热路径使用 `*_async` 版本；文档列出每个 API 的「同步/异步」属性与默认超时。新仓库不承诺与 zcbot API 逐签名兼容，只提供迁移指南。

## 5. 数据访问：DB 代理与事务语义

### 5.1 硬规则

- **Core 持有唯一 SQLite 连接，是唯一写者。** Worker 一律通过 `RemoteDatabase` 代理访问，**禁止** Worker 直接打开/写 DB 文件。
- Core 内部用**单写者队列**按提交顺序串行执行写操作，天然规避多进程 `SQLITE_BUSY`；DB 使用 WAL 模式 + `busy_timeout`。

### 5.2 必须回 Core 串行化的操作

- 全部 INSERT / UPDATE / DELETE / DDL。
- 任何「读-改-写」事务（自增计数、抢占任务、状态机流转）——因为需要原子性。
- 需要与写操作原子一致的操作（如写 DB + 发消息的业务事务边界，按写意图由 Core 编排）。
- 写操作携带**幂等键**，超时重试不得重复落库。

### 5.3 可以并行/就地完成的操作

- 纯读：阶段一统一经 Core 读；阶段二引入每 Worker **只读副本连接（WAL 快照）** 或 Core 侧并发读池，快照延迟写入文档。
- 已取回数据在 Worker 进程内的 CPU 计算、缓存、聚合。
- 非 DB 且天然可分片的资源（如 Worker 本地内存缓存）无需回 Core。

### 5.4 事务语义

- 远端事务：`BEGIN` 向 Core 申请**写者租约**；同一 Worker 内可嵌套/savepoint；`COMMIT/ROLLBACK` 经代理完成。
- 租约超时自动释放；**Worker 死亡时 Core 强制回滚其未提交事务**（对应 3.5 死亡清理）。
- **禁止跨 Worker 分布式事务**（不做 2PC）：需要跨 Worker 一致性时，改为向目标 Worker 发命令编排，或重构数据归属。

## 6. 起步路径：从零到能跑的三个阶段

### 阶段一 — 单 Core + 单 Worker，跑通 IPC 边界

- **范围**：Core 持有 DB/协议接入/IPC Server；只有 1 个 Worker 加载全部示例插件；`RemoteDatabase` / `RemoteApiCaller` 可用；监督器支持限流重启；事件至少一次投递 + ACK。
- **验收标准**：
  1. 示例插件能收到事件、经代理完成一次 DB 写和一次消息发送。
  2. `kill -9` Worker → Core 5 秒内检测、30 秒内重启、`max_restarts=5 / 30s` 生效；期间网关与 DB 可读；未 ACK 事件被重投，消费端去重后无重复副作用。
  3. 插件在 hook 里抛异常不会杀死 Worker，能被记录。
  4. 记录基线：单次 DB 写 RPC 的 p99 延迟（量化「一次序列化往返」的代价）。

### 阶段二 — 1:N Worker + 路由 + 注册聚合

- **范围**：可配置隔离粒度（分组 + `untrusted` 独占）；Worker 注册表；事件订阅索引与按 key 分片；命令注册表聚合与重名检测；每 Worker 独立攒批；背压/慢 worker 降级；超时与取消。
- **验收标准**：
  1. 10 个 Worker / 约 30 个插件运行；杀死 1 个 Worker，只有它的命令返回「不可用」，其他命令 p99 延迟变化 < 10%。
  2. 命令重名在注册期被拒绝并给出清晰诊断。
  3. 模拟慢 worker（handler sleep 2s）不阻塞其他 worker；丢弃计数与 DEGRADED 状态可观测；总线无队头阻塞。
  4. 同一 key 的 1000 条事件按顺序投递到同一个 Worker，且顺序正确。
  5. `CANCEL(request_id)` 能让进行中的命令停止回传结果，无孤儿回调。

### 阶段三 — 熔断 / 网关拆分 / 读优化 / 运维

- **范围**：熔断禁用与显式恢复；可选 Gateway 进程承载协议接入；只读副本加速读；运行时增删 Worker（扩缩容）；管理端查看注册表、重新启用被禁用插件。
- **验收标准**：
  1. 抖动插件（30s 内崩 5 次）被自动熔断禁用、发出管理告警，其他插件不受影响；管理员可手动恢复。
  2. 杀死 Gateway → Core 重新拉起并重绑端口；Worker 持续运行，缓冲事件最终送达。
  3. 运行时新增 Worker → 其命令无需重启 Core 即出现在全局命令表。
  4. 交付一份「故障矩阵 + 运维 runbook」（崩溃/超时/背压/重名/版本不兼容各类现象与处置）。

## 7. 明确不做什么（防范围膨胀）

1. **不改 zcbot、不做兼容包装。** 不修改 zcbot 任何一行；不把 zcbot-mp 做成其分支、wrapper 或配置开关。zcbot-mp 是独立仓库、独立发布，不与 zcbot 共享运行时代码。
2. **不做跨机器分布式。** Worker 只由 Core 在本机 spawn，IPC 只走本机回环 + authkey；不做远程 Worker 注册、不做集群、不做 Raft/etcd/服务发现。失败域是「本机进程」，不是「跨机节点」。
3. **不做 zcbot 插件/API 的逐签名兼容层。** 不承诺直接加载 zcbot 现有插件或保持 `ctx.*` 全部签名一致；只提供 API v1 契约与迁移指南，插件需按新契约适配。
4. **不做跨 Worker 分布式事务 / Worker 直连写 DB。** 只保留 Core 单写者 + 幂等写 + 租约回滚；不引入 2PC/补偿框架的复杂度。
5. **不做插件安全沙箱。** 本地 Worker 是可信代码，OS 进程隔离是故障隔离而非安全边界；不做不可信代码执行、权限沙箱、容器隔离。
6. **不做「热替换运行中 Worker 代码」的魔法。** 插件变更一律通过重启对应 Worker 生效；阶段一/二不做花哨 WebUI 或任何语言的对外 SDK。

## 附：一句话总结决策链

> 新仓库默认多进程 → Core 独占资源与单写者、Worker 只跑插件 → 1:N 带来的身份/路由/注册/背压/重启/超时问题全部在 Core 侧集中解决 → 插件用声明式 manifest + 同步声明 API + 异步跨进程 API → DB 写回 Core 串行化、读可并行 → 先用单 Worker 跑通 IPC，再上 1:N，最后补熔断与运维 → 守住「不动 zcbot、不跨机、不兼容层、不 2PC、不沙箱」五条边界。
